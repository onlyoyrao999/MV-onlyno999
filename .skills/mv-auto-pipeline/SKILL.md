# MV-AUTO-PIPELINE · 音乐 MV 全自动生成 SOP (V1.0.6)

> **核心承诺**：一首歌 + 一张图，出来一支口型对得上的 MV。
>
> AI 做的 MV，第一眼就露馅的地方不是画面不够炫，也不是脸不像，而是**嘴和歌对不上**：
> 1. 第二句歌词正在唱，画面里的人却已经闭嘴了；
> 2. 远景里走路的人莫名其妙在张嘴；
> 3. 好不容易拼完，整片比音乐慢了半拍。
>
> 这三件事，是本 Skill 存在的全部理由。

## MV 垮在哪儿：三大结构性硬伤

以下三条是真正会毁掉整片的根源 —— 不是审美问题，而是底层工程结构问题：

### 01. 时间轴没有根
段长靠感觉定，切点靠眼睛找 → 第一段就已经错位，后面全是补丁。切点必须死死锚定在歌词时间轴与乐句呼吸点上。

### 02. 口型乱套
一句一句都让人开口，远景、空镜、背影也全在唱 → 假得最明显，观众迅速审美疲劳。**只有中近景才能开口，远景全景必须硬闭嘴**。

### 03. 音画慢慢漂走
主流视频生成模型每段输出都会随机多出 `0.1s ～ 0.4s`。二十几段累加下来，画面已经漂到音乐后面数秒甚至更远，且通常剪到第 5 段才被察觉。

## 六条不可动摇铁律 (Iron Rules)

下面这些不是「建议」，是写死在流水线里的不可动摇条款（除非用户在提示中明示覆盖）：

### 铁律 A：音乐是唯一的时间基准
* 段长、切点、口型位置全部从歌词时间轴推导，**绝对禁止先想好画面再去凑音乐位置**。
* 歌词一行不能少（主歌、副歌、重复段、和声行、桥段全部在列）。
* 间奏（Intro、Interlude、Solo、Outro）必须显式打标切出，它直接决定镜头节奏与呼吸感。

### 铁律 B：只有中近景才对口型
* **允许对口型的景别仅限四类**：`大特写 (Extreme Close-Up)`、`特写 (Close-Up)`、`近景 (Medium Close-Up)`、`中景 (Medium Shot)`。
* **中远景、全景、大远景、空镜、背影、群像一律严禁对口型**，由机器硬校验拦截。
* **口型节奏克制**：全片口型段目标占比控制在 **40% ~ 50%**（基准 45%）。**连续对口型不得超过 3 段**，中间必须强制插入叙事镜头、空镜或氛围群像。

### 铁律 C：唱歌不是说台词
* 发声行必须走官方歌唱专用框架，**一句歌词独立成行**。绝不能写成「说某某话」或「念诵台词」，否则模型必驱动人物产生说话口型。
* **不对口型的段落必须显式压制**：正文中一旦出现歌唱标记，模型极易产生跟随动作。因此不对口型段必须强制注入正向声明：`"mouth naturally closed, lips completely still, not moving along with vocals"`，并在负面提示词中注入：`"singing, mouth open, lip-sync, talking, speaking, vocalizing"`。
* 语言严格分层：**字段名、技术参数与视觉标签用英文；艺术叙述、人物情感与原歌词用中文**。

### 铁律 D：工作流与生成：不猜、不烧冤枉钱
* **先体检后改造**：先读取宿主工作流真实的节点表与参数契约，绝不按臆测的字段名提交。契约校验失败直接拒绝发起任务。
* **共享模板彻底去参考化**：清除上一位用户残留的种子图、噪声与参考音频，防止人物长相杂交污染。
* **母带与资产指纹缓存**：全片母带音频与参考人物图仅上传一次，利用 SHA-256 指纹复用，拒绝重复上传。
* **三开关独立原则**：`账号降级 (Fallback)`、`双池并行 (Dual Pool)`、`真钱封顶 (Budget Cap)` 是三个独立开关，互不推定（用户给了 API Key 不等于授权扣除付费余额）。

### 铁律 E：八道关 + 对齐三验
* **双关制**：每道门禁均由「机器自动化规则硬检」+「HTML 可视化人工交互确认」组成。即便用户开启全自动放权，机器自检与硬门禁依然全量执行，放权的是审批人，不是免除质检。
* **对齐三验不过，不许宣称交付**（详见后文对齐三验机制）。

### 铁律 F：会自己长本事（自演进闭环）
* 每支 MV 跑完必须触发**「复盘三问」**：
  1. 实测与预设偏差多大？
  2. 哪一步翻车或产生返工？
  3. 哪个经验可固化为代码或规则？
* 沉淀必须同时更新：**代码、参考文档、自检清单**，三处同步才算修复。每次改版打 Git Tag 快照，老修复丢失则拒绝合并。

## 十二步全流程与八道门禁

```
[音频输入 + 歌词] 
       │
   (关 1: 歌词提取与强制对齐)
       │
   (关 2: 风格锁定) ──→ (关 3: 人物与资产)
       │
   (关 4: MV 分镜设计)
       │
   [关 5 · 硬门禁: 提示词派生 & 11项机检]
       │
   [关 6 · 硬门禁: 音乐窗口与口型核对]
       │
   [工作流体检 + 首镜试产验证]
       │
   [批量生成 (双池并行 + 断点续跑)]
       │
   [重抽卡 (针对单段微调，无依赖重试)]
       │
   (关 7: 拼接成片) ──→ (关 8: 对齐三实验收)
       │
   [项目复盘与规矩沉淀发版]
```

### 详细步骤与门禁清单：
1. **歌词提取与强制对齐 (Gate 1)**：
   - ASR 语音识别负责提供毫秒级时间戳候选；
   - 官方歌词进行词级 Levenshtein 纠偏；
   - 标记 `[Verse]`, `[Chorus]`, `[Bridge]`, `[Solo]`, `[Outro]` 与器乐空白段；
   - 产出时间轴基准。
2. **风格锁定 (Gate 2)**：
   - 确立美术基调（赛博朋克、新中式国潮、胶片复古、日系吉卜力、黑白暗黑电影感等）；
   - 锁定色彩空间 (LUT)、光影质感与画幅比例 (16:9 / 9:16 / 2.39:1)；
   - **必须在人物资产前锁定**，避免服装色调重复返工。
3. **人物与资产 (Gate 3)**：
   - 生成/确认主人公多角度面部图、体型与核心服装参考；
   - 生成关键场景与标志性道具；
   - 若走无主角模式，此步跳过人物面容，重点确立场景空间图集。
4. **MV 分镜设计 (Gate 4)**：
   - 依乐句与呼吸点切割视频镜头；
   - 切点仅落在歌词行尾，严禁将单句歌词跨镜头切割；
   - 初步指派景别、运镜、角色动作与口型开关。
5. **提示词派生 (Gate 5 · 硬门禁)**：
   - 逐段生成六段式提示词，严格执行 11 项机检，未全绿严禁下发；
   - 计算提示词 SHA-256 指纹，一旦修改自动废除旧审批。
6. **音乐窗口与口型核对 (Gate 6 · 硬门禁)**：
   - 校验窗口首尾相接无间隙、无重叠，总时长 `∑(End - Start) == TotalDuration`；
   - 校验景别与口型标记逻辑合规；
   - 严禁任何手写秒数；
   - 门禁未放行前，**不向算力后端提交任何视频生成请求**。
7. **工作流体检与改造**：
   - 动态拉取后端 ComfyUI / API 真实节点与入参 schema；
   - 注入防串色与去模板化污染补丁。
8. **首镜试产 (First Shot Pilot)**：
   - 抽检第 1 个中近景对口型镜头进行单镜全流程实测；
   - 校验分辨率、编码器格式、音频重采样兼容性。
9. **批量并发生成**：
   - 队列管理、双池并发；
   - 10~15 分钟心跳进度上报；
   - 断点持久化，在途任务自动关联救回。
10. **单段重抽卡 (Reroll)**：
    - 针对个别崩坏片段独立重跑；
    - 段间解耦零依赖；若改写提示词，退回关 5 重审。
11. **时长贴合与拼接成片 (Gate 7)**：
    - 执行帧网格裁切或智能帧率时间拉伸；
    - 画面轨合成并强制压入原曲母带。
12. **对齐三实验收与项目复盘 (Gate 8)**：
    - 自动跑对齐三验（滞后量、波形相关度、人声能量）；
    - 生成复盘文档并回填优化项至 Skill 规则库。

## 两大独创自研算法机制

### 机制一：时长贴合 (Duration Fitting)
* **问题痛点**：视频扩散模型生成的片段往往不是精确整数秒（例如请求 4.0s，由于 FPS 舍入与解码延迟，常输出 4.12s 或 3.88s）。多段相加导致雪崩式音画错位。
* **算法解法**：
  1. 请求时长向上对齐到帧网格（Frame Grid）：`RequestFrames = ceil(TargetSeconds * FPS)`；
  2. 视频落盘后，通过精准时间基准 `pts` 截取或填充，强制裁剪到该分镜段窗口 `[Start, End]` 的理论微秒长度；
  3. 保证 `∑ SegmentDuration === MasterTrackDuration`，彻底根绝漂移。

### 机制二：对齐三验 (Three-Fold Alignment Verification)
* **传统互相关瓶颈**：整片全量做音频交叉相关计算需要十亿次级浮点计算，耗时且易被混响背景乐误导。
* **自研轻量解法**：
  1. **音频包络提取 (Envelope Extraction)**：对提取出的人声音频与母带参考音轨提取 RMS 能量包络，数据量压缩 100 倍；
  2. **局部搜索极值 (Local Lag Search)**：仅在理论切点邻域 `[-300ms, +300ms]` 窗口内搜索最佳时移 $\tau$；
  3. **三大硬判据**：
     - **最优滞后量 (Optimal Lag)**：$|\tau| \le 80\text{ ms}$（小于两帧偏差）；
     - **归一化互相关系数 (Normalized Cross-Correlation)**：$r \ge 0.78$；
     - **人声能量存在性 (Vocal Energy)**：口型段人声 RMS 能量阈值 $> -36\text{ dBFS}$。
* 纯标准库数秒内出具对齐验收报告。

## 关 5 硬门禁：11 项提示词机检清单

第 5 关为代码级自动化断言，11 项必须全部为 `PASS`：
1. **六段式结构完整性**：必须具备 `[SHOT]`, `[SUBJECT]`, `[ACTION]`, `[ENVIRONMENT]`, `[LIGHTING_COLOR]`, `[CAMERA_TECH]` 六大区块。
2. **语言分层校验**：结构键名与摄影参数采用英文，人物情感与叙述描述采用中文。
3. **独立发声行**：对口型镜头必须且仅能以独立行标注：`Singing vocals: "歌词文本"`，严禁融入叙述性句子。
4. **禁止台词化动词**：正文中绝对禁止出现 `"saying"`, `"speaking"`, `"talking"`, `"shouting"` 等对白类动词。
5. **景别匹配约束**：若标记为口型段，景别必须断言属于 `[ECU, CU, MCU, MS]` 四类之一。
6. **非口型段正向嘴唇压制**：非口型镜头必须包含嘴唇自然闭合声明：`"mouth naturally closed, lips completely still, not moving along with vocals"`。
7. **非口型段负向词压制**：非口型镜头的 Negative Prompt 必须包含：`"singing, mouth open, lip-sync, talking, speaking, vocalizing"`。
8. **角色一致性锚点**：有主角模式下，必须包含角色识别特征锚点与参考图指纹引用。
9. **无违禁词与冲突描述**：无前后矛盾（如同时出现 `"night"` 与 `"bright direct sunlight"`）。
10. **动作节奏与时长匹配**：不得在 3 秒窗口内安排超过 2 组复合剧烈身体运动。
11. **提示词防篡改指纹**：计算提示词 Hash，任何改动都会使旧放行批文失效。

## 关 6 硬门禁：音乐窗口与口型核对规范

第 6 关核查数学关系与分镜生理节奏：
1. **数学无缝闭环**：
   - 镜头 0 的 `Start == 0.000`；
   - 任意镜头 $i$ 的 `Start == 镜头 (i-1) 的 End`；
   - 最后一个镜头的 `End == 全曲音频总时长`；
   - 严禁任何手工四舍五入引发的时长空隙。
2. **景别与口型一致性**：
   - 检查所有标有 `is_lip_sync: true` 的分镜，其景别必须是特写或中景；
   - 远景、空镜、环境镜头如果标注了口型，一票否决。
3. **口型密度与疲劳度控制**：
   - 全片对口型时长占全曲总时长比率须维持在 **40% ~ 50%**（黄金中位 45%）；
   - **连续对口型镜头计数器 $\le 3$**，出现连续 4 个口型镜头强制打回，必须插入空镜/叙事/群像缓冲。

## 双池调度、断点续跑与成本台账

* **四级凭证自愈读取**：
  1. 本地项目环境变量；
  2. 用户主目录全局配置 (`~/.config/mv-pipeline/credentials.json`)；
  3. 密钥管理中枢；
  4. 交互式录入（仅首次缺失时唤醒）。
* **双池调度机制**：
  - **免费/低优先级池 (Community / Spot Pool)**：承载试产与常规镜头；
  - **优先/付费池 (Priority / Paid Pool)**：承载重抽或紧急镜头；
  - 严格遵守**真钱封顶约束 (Budget Cap)**，达标自动转挂起并等待人工确认。
* **在途任务救回**：系统重启或中断时，启动时先拉取远端 TaskID 状态，存在则直接挂接等待，杜绝重复消耗算力。

## 自进化与版本沉淀机制

每次 MV 项目完成后必须执行复盘，演进流程如下：
1. 记录实际产出指标（对齐三验得分、重抽次数、异常片段）；
2. 执行**复盘三问**并提取工程规矩；
3. 将修复更新到：
   - `scripts/` 下的校验与对齐脚本；
   - `references/` 下的标准作业文档；
   - 运行自动化测试，验证老用例不回退；
4. 递增版本号并打上 Snapshot 标签。

## 交互问询协议与使用指南

当用户启动本 Skill 时（例如提供了一首歌与图片），**先礼貌收集六大前置决策项**：
1. **歌曲文件**：确认格式、音轨时长与是否附带官方歌词；
2. **主人公模式**：是否提供主人公参考图，或选择「无主角氛围模式」；
